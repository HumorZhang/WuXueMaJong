## 一、总体原则

1. **先单机，后联网**：规则逻辑在单机阶段完全跑通、测试覆盖后，再接入网络层。
2. **核心逻辑独立于 Unity**：规则引擎写成纯 C# 库，客户端与服务器共用，可用单元测试/控制台快速验证。
3. **服务器权威（Authoritative Server）**：牌局状态只存在于服务器，客户端只发送操作意图，防作弊从架构层面保证。
4. **每个里程碑可运行、可演示**：不做「一次性大爆炸集成」。

## 二、阶段 0：规则与需求定义

> 预计：1~2 周 · 产出物：《规则文档》

### 2.1 确定麻将规则体系（最重要的决策）

规则决定数据结构、算法、UI 与服务器设计。候选方案：

| 规则 | 特点 | 实现难度 |
|---|---|---|
| **四川麻将（血战到底）** | 无吃、只有万筒条、缺一门、血战到底 | ★★ 推荐 MVP |
| 广东麻将 | 有吃、推倒胡、鸡胡较多 | ★★ |
| 国标麻将 | 81 番种、计分复杂、竞技性强 | ★★★★★ 不建议首版 |
| 日本立直麻将 | 役种体系、立直/振听、宝牌 | ★★★★ |

**建议**：MVP 采用四川麻将或自定义极简规则（武侠题材可包装为自创玩法，如「内功」「门派」等机制后续再扩展）。

### 2.2 编写《规则文档》

必须以**可测试的条款**形式明确：

- [ ] 牌张构成（万/筒/条/风/箭/花各多少张）
- [ ] 吃、碰、明杠、暗杠、补杠、抢杠胡细则
- [ ] 胡牌条件：自摸/点炮、一炮多响、截胡
- [ ] 番/役计算表（MVP 先定义 5~10 个番种）
- [ ] 结算公式（底分、番数上限、庄家连庄）
- [ ] 流局/荒庄处理（查大叫、退税等，按规则）
- [ ] 庄家轮转与局数规则（东风圈/自定义）
- [ ] 操作优先级（胡 > 碰/杠 > 吃）与响应窗口
- [ ] 超时规则（出牌倒计时、自动摸打）

### 2.3 网络玩法需求

- [ ] 游戏模式：好友房 / 匹配 / 人机 / 排位
- [ ] 断线重连、超时 AI 托管
- [ ] 目标平台：PC / Android / iOS / WebGL（影响网络方案与 UI 设计）
- [ ] 商业化方向（纯买断 / 皮肤 / 广告；**避免真钱赌博**）

## 三、阶段 1：技术架构选型

> 预计：1 周

### 3.1 代码分层

```
WuXueMaJong.Core     ← 纯 C# 规则引擎（牌墙、动作、胡牌判定、番种、结算）
       ↑ 被引用
客户端（Unity）      服务器（.NET）   ← 二者共用 Core，服务器做权威判定
```

- Unity 中使用 **Assembly Definition** 将 Core 与客户端代码隔离
- Core 不依赖 UnityEngine 命名空间，可用 xUnit/NUnit 直接测试

### 3.2 网络方案

| 方案 | 说明 | 结论 |
|---|---|---|
| **独立 .NET 权威服务器 + WebSocket** | 完全掌控、防作弊、易扩展 | ✅ 推荐 |
| Unity Netcode / Mirror | 开发快，但权威逻辑仍应放服务器 | 备选 |
| Photon / Colyseus | 托管服务，省运维但付费且逻辑受限 | 备选 |

> 麻将的特点：回合制、低频同步、高度隐藏信息 → **事件驱动 + 服务器权威**是最佳模型，不要用帧同步。

### 3.3 配套技术栈（建议）

- 协议：Protobuf（推荐）或 JSON
- 数据库：PostgreSQL/MySQL（账号、战绩）；Redis（房间状态、匹配队列、会话）
- 后端框架：ASP.NET Core（.NET 8+）
- CI/CD：GitHub Actions（Core 单元测试 + 构建）
- 版本管理：Git（已初始化，远端 GitHub）

## 四、阶段 2：核心逻辑原型

> 预计：3~6 周 · 目标：控制台里 4 个 AI 能自动打完一整局

- [ ] **牌模型**：牌张编码、手牌/牌墙/牌河/副露数据结构
- [ ] **牌墙系统**：服务器端洗牌、发牌、摸牌顺序、海底牌
- [ ] **动作系统**：摸、打、吃、碰、杠（明/暗/补）、胡、过
- [ ] **胡牌判定**：递归拆解「面子 + 将牌」，查表/记忆化优化
- [ ] **番种判定 + 结算**：先 5~10 个番种，计分公式配置化
- [ ] **听牌 / 向听数计算**：为 AI 与「听牌提示」功能服务
- [ ] **回合状态机**：轮转、响应优先级、一炮多响/截胡处理
- [ ] **单元测试**：牌型、海底、杠上开花、抢杠、流局等边界全覆盖
- [ ] **简单 AI**：启发式出牌（打孤张、保搭子、能胡则胡）

**里程碑 M1：规则引擎完整、单元测试通过、控制台可完整跑局**

## 六、阶段 4：联网架构

> 预计：6~10 周 · 本项目最大难点

- [ ] **权威服务器**：牌局状态只存在于服务器
- [ ] **隐藏信息隔离**：每家只收到自己的手牌 + 公开信息
- [ ] **协议设计**：登录 / 房间 / 准备 / 开局 / 动作 / 广播 / 结算 / 重连快照
- [ ] **同步模型**：服务器按序广播事件，客户端按序播放；重连下发全量快照
- [ ] **房间管理**：创建、加入、准备、启动、解散；好友房 + 匹配队列
- [ ] **断线重连**：会话令牌、状态恢复、超时 AI 托管
- [ ] **防作弊**：动作合法性校验（轮次/牌张/频率）、服务器随机数、日志审计
- [ ] **异常容错**：超时、掉线、服务器重启后对局恢复

**里程碑 M3：4 人真实联网对战跑通**

## 十、贯穿始终的工程实践

- **Core 单元测试先行**：整个项目的地基
- **规则参数配置化**：不写死，方便换规则与调平衡
- **回放系统**：同时用于测试、反作弊、观战
- **日志与埋点**：客户端与服务端统一格式
- **分支策略**：`main` 保护 + 功能分支（feature/xxx）
- **持续集成**：每次 push 自动跑 Core 测试
- **文档同步**：规则、协议、架构变更即更新 Docs

## 十一、风险提示

| 风险 | 对策 |
|---|---|
| 规则复杂度失控（尤其番种） | MVP 只做子集，配置化扩展 |
| 隐藏信息 + 断线重连 | 服务器权威从第一版就定死，不后补 |
| 美术成本高 | 全程占位素材，最后替换 |
| 个人开发周期长 | 按 M1→M4 顺序推进，每个里程碑可停可评估 |
| 服务器运维成本 | 初期单服即可，WebSocket + Redis 足够 |
